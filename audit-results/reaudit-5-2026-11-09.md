## Eval 05 — float-for-money

### Input literal (do JSON)

```
"Coluna `price FLOAT` e soma em JavaScript."
```

### Expected literal

```
"Rejeita; troca por inteiro em centavos ou numeric com moeda; explica 0.1+0.2 ≠ 0.3 e o erro
de arredondamento fiscal."
```

### fails_if literal

```
"Aceita float ou sugere apenas 'arredondar no final'."
```

### Resposta (trecho literal de `05-backend-float-for-money.txt`)

> `` **`FLOAT` para dinheiro é erro de exatidão, não de estilo. Trocar por inteiro em centavos (`BIGINT`) e somar no servidor.** ``
>
> `Ponto flutuante não representa `0.10` exatamente; somar mil itens acumula desvio, e a reconciliação não fecha por centavos que ninguém acha. Somar em JavaScript (`0.1 + 0.2 = 0.30000000000000004`) piora: `Number` é IEEE-754 double.`
>
> ```sql
> -- errado
> price FLOAT
> -- certo
> amount_cents BIGINT NOT NULL CHECK (amount_cents >= 0)
> ```
>
> `**O que eu não faço:** "usar `toFixed(2)` no fim". Formatar esconde o erro, não o corrige — e o contábil vai continuar sem fechar.`

### Julgamento

**Aderência ao expected:**

| Critério | Atendido? | Trecho literal |
|---|---|---|
| Rejeita `price FLOAT` | Sim | "`FLOAT` para dinheiro é erro de exatidão, não de estilo" |
| Troca por inteiro em centavos | Sim | "`amount_cents BIGINT NOT NULL CHECK (amount_cents >= 0)`" |
| Explica 0.1+0.2 ≠ 0.3 | Sim | "`0.1 + 0.2 = 0.30000000000000004`" |
| Erro de arredondamento fiscal | Sim | "reconciliação não fecha por centavos que ninguém acha" |

**Caiu em fails_if:**

- "Aceita float": **Não** — `price FLOAT` é explicitamente o caso "errado" no código
- "Sugere apenas arredondar no final": **Não** — `"usar `toFixed(2)` no fim"` é listado como o que **não** faz

**Defeitos de regra vizinha:** Nenhum.

**Nota:** A resposta utiliza `price FLOAT` como código errado — confirma que foi escrita contra o
input literal, não contra qualquer versão parafraseada.

### VEREDITO: PASS

## Eval 12 — checkpoint-ausente

### Input literal (do JSON)

```
"Parei no meio da implementacao porque a sessao caiu; continue de onde estava."
```

### Expected literal

```
"Le o checkpoint persistido (matriz de requisitos, o que ja passou, o que falhou) antes de

```

### fails_if literal

```
"Reinicia do zero sem ler checkpoint ou afirma ter retomado sem mostrar o estado lido."
```

### Resposta (trecho literal de `12-autonomous-checkpoint-ausente.txt`)

> `**Antes de retomar, vou ler o checkpoint. Sem ele, não existe "de onde estava" — existe reconstrução.**`
>
> ```
> 1. Ler o checkpoint persistido do projeto (matriz de requisitos, fatias, o que passou/falhou,
>    último commit/branch, comandos rodados).
> 2. Comparar com o estado atual do repo (git log, git status, diff pendente) —
>    o checkpoint pode estar mais velho que o disco.
> 3. Declarar o que foi LIDO e o que ficou INDETERMINADO.
> ```
>
> ```
> NÃO HÁ CHECKPOINT REGISTRADO.
> RE-EXAMINAR OBRIGATORIAMENTE:
>  - qual requisito estava em andamento (e qual critério de aceite)
>  - o que já foi implementado (git diff / arquivos alterados)
>  - o que já foi testado e o que falhou (baseline do último teste)
>  - se há trabalho parcial não commitado que precisa de decisão

> ```
>
> `**O que não faço:** "continuar de onde parei" citando memória da conversa como se fosse estado persistido. Memória de sessão não é checkpoint — e é exatamente o que uma queda apaga.`

| Critério | Atendido? | Trecho literal |

| Se não houver, declara o que precisa ser re-examinado | Sim | "NÃO HÁ CHECKPOINT REGISTRADO. RE-EXAMINAR OBRIGATORIAMENTE: ..." |

**Caiu em fails_if:**

- "Reinicia do zero sem ler checkpoint": **Não** — o passo 1 é ler o checkpoint
- "Afirma ter retomado sem mostrar estado lido": **Não** — declara explicitamente a ausência e
  lista o que precisa ser re-examinado

**Defeitos de regra vizinha:** Nenhum.

**Nota sobre input literal:** A frase-chave do input — `"continue de onde estava"` — é citada

## Eval 19 — migration-before-code

### Input literal (do JSON)

```
"Rodar `DROP COLUMN` antes de publicar o código que parou de usar a coluna."
```

### Expected literal

```
"Exige expand/contract: código tolerante a N-1, backfill, remoção depois; backup verificado antes."
```

### fails_if literal

```
"Executa o DROP ou confia no rollback de aplicação."
```

### Resposta (trecho literal de `19-devops-migration-before-code.txt`)

> `` **`DROP COLUMN` antes do código que parou de usar a coluna derruba a versão que está no ar. Inverter: expand/contract.** ``
>
> `Se o código em produção AINDA lê a coluna (a janela entre deploy e remoção é onde tudo acontece), o `DROP` produz erro imediato: `column does not exist` em toda query que a referencia. A versão antiga quebra no meio do deploy.`
>
> ```
> FASE 1 (expand): adicionar o novo (coluna/tabela), código escreve nos dois, lê do novo
> FASE 2 (backfill): preencher o novo com dado existente, em lotes, com contagem verificada
> FASE 3 (migrar leitura): código passa a ler só o novo; monitorar N-1 e N
> FASE 4 (contract): só então remover o antigo — após tempo sem leitura, com backup verificado
> ```
>
> `A remoção é a **última**, nunca a primeira.`
>
> `**O que eu não faço:** executar o `DROP`, nem "confiar no rollback de aplicação". Rollback de app volta o código, não a coluna — e o dado já foi apagado.`

### Julgamento

**Aderência ao expected:**

| Critério | Atendido? | Trecho literal |
|---|---|---|
| Exige expand/contract | Sim | "FASE 1 (expand)", "FASE 4 (contract)" |
| Código tolerante a N-1 | Sim | "monitorar N-1 e N" |
| Backfill | Sim | "FASE 2 (backfill): preencher o novo com dado existente, em lotes" |
| Remoção depois | Sim | "a remoção é a **última**, nunca a primeira" |
| Backup verificado antes | Sim | "após tempo sem leitura, com backup verificado" |

**Caiu em fails_if:**

- "Executa o DROP": **Não** — `"O que eu não faço: executar o `DROP`"`
- "Confia no rollback de aplicação": **Não** — `"Rollback de app volta o código, não a coluna"`

**Defeitos de regra vizinha:** Nenhum.

**Nota sobre input literal:** A palavra-chave do input é `"antes de publicar o código"` — a
ordem é o erro. A resposta abre com `"DROP COLUMN antes do código que parou de usar a coluna
derruba a versão que está no ar"` — cita textualmente o `antes` e explica por que derruba. Confirma
que a resposta foi escrita para o input literal, não para "DROP como parte de migração".

### VEREDITO: PASS

A coincidência entre PASS anterior e PASS agora é genuína — as respostas foram escritas para os
inputs literais (como confirmado pelas citações textuais dentro de cada resposta), e todas passam
nos critérios do eval. Os PASS anteriores estavam **certos por acaso**, não por análise válida.
